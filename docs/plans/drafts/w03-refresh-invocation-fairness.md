### Concrete shared-seam proposal for serial release

Use the existing durable page as the admission quantum: at most one50-key cached-refresh page per provider invocation, checkpoint after effects, then pending if the terminal read has not yet occurred. One page guarantees forward progress; the next invocation performs the terminal read if needed. This count is based on the established actual-store unit, not a test wall cutoff. Existing `runSliced` continues to measure elapsed awaited work using performance.now and the8ms local target; no new hosted wall timeout is proposed. Add an explicit platform yield even when a page has no flag updates/all404s. This bounds the cached-refresh phase only: enumeration, flag reconciliation and attachment repair need their own ownership decisions before claiming the whole provider invocation is bounded.

Proposed `MailProvider.sync` result: completed (legacy void remains completed for other providers) or `{ pending: true }`. Backend records pending under current account lifetime/credential identity, releases the active invocation, and schedules exactly one continuation via platform.yield when connectivity/auth/cooldown admission permits. Pending is distinct from syncAgain and flag intents. Offline/backoff/auth/cooldown state retains the continuation until the existing corresponding network/sign-in/cooldown event; no immediate retry when blocked, no timer spin. `dropAccount`/credential replacement invalidates the continuation identity. `autoSync:false` still continues an explicitly requested logical sync, but creates no startup or periodic work. `syncAccount` should await its admitted invocation; tests needing the full logical drain must explicitly join its finite continuations (do not accidentally recurse/chase an unbounded promise chain).

Per-invocation finally ends arrivals and releases admission. Pending retains logical-pass eviction/attention ownership; it must not call passDone/attention.prime or imported-draft restore, emit sync.done, set idle/lastSyncAt or resume auth/network ops. A valid successful page may settle physical provider admission but must not declare logical sync complete. Completion runs those existing effects once. Core must decide whether to preserve the logical observation token across continuations or start a fresh observation with equivalent ownership; this is a concrete W02 flag-contract dependency, not permission for a Gmail-only bypass.

For the missed identity, the store transaction that creates/rebinds the account/provider identity must coalesce a refresh-needed generation keyed by local message identity and current provider binding. Prefer extending the current pending snapshot machinery if W02 confirms its flag ownership semantics permit it; otherwise add a persisted scalar generation on the message plus a bounded indexed pending reader. Storage is O(existing messages), not a history/event ledger. Effects and acknowledgment must compare provider binding, lifetime/credentials and captured generation, so an old read cannot clear a newer admission. Delete removes its obligation; promotion updates its binding without changing body/asset ownership. Account completion atomically checks pending generation before dropping the account continuation; admission racing after that check must retain/wake pending work through the existing store-change event. Root/W02 must provide this shared write/read/ack contract before Gmail drains it. No cursor reset, per-mailbox copied snapshot, volatile side ledger or unwired helper is acceptable.
