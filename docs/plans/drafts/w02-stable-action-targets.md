### Implementation design before source

Use the existing draft_counter pattern: one durable category_counter singleton, positive safe-integer IDs, monotonically increasing last_id in the same transaction as creation. SQL appends migration33, without rebuilding categories or rewriting any historical migration, preserving all category FKs/indexes/triggers. SQL insertion triggers advance the counter for explicit fresh IDs and refuse reuse of retired IDs; category primary-key updates are refused. createCategory chooses counter+1 in a transaction; exhaustion refuses before unsafe numeric IDs. No sentinel, random range, per-filter ledger or lifetime side service.

Migration seeds the ceiling from live category IDs, retained filter action categoryId references, pending-import categoryId references and move-journal category_id/source-from references, including deleted targets above live max. New filter saves also reserve numeric category references, preventing a newly saved nonexistent ID from becoming a future category. SQL filter insert/update triggers keep raw recovery writes within this invariant. IDB uses a physical version20 upgrade and logical schema33, with an early-loaded counter and transactional creation/filter reservation. IDB's established in-memory highestKey also covers explicit in-memory fixture inserts; supported category creation/import/seed paths use createCategory. Physical upgrade scans stored references with guarded cursors, preserving existing uncertainty/atomic-upgrade behavior. No changes to generic MemDb, ingest, classifier or operation engines.

Native/WASM numeric SQL explicit insertion is permitted only for a fresh ID above the persisted ceiling; restoring a retired explicit ID is refused. IDB has no public explicit-category-ID recovery API; persisted legacy IDs are loaded unchanged and reserved by upgrade. Ordinary application backup import deliberately maps exported IDs by category name into newly allocated local IDs, and then remaps rule actions/pending filters; exported IDs are not inserted directly. Full database images preserve the counter. Seed paths already call createCategory. No backup format change or silent rule reset.

Preexisting aliases (a removed category already replaced with the same ID before upgrade) have no distinguishable lifetime provenance: keep those current rules unchanged, do not disable all rules or claim historical unmixing. An erased legacy ID with no surviving reference anywhere cannot be reconstructed; migration reserves all supported retained category references, not unknowable external stale clients. Counter bounds preserve safe integer semantics; exhaustion is an explicit allocation error. Committed-but-unacknowledged creates retain their consumed IDs; retries may create another category (existing non-idempotent API), but cannot reuse the committed ID. A rolled-back, never-published allocation may be reused safely.
