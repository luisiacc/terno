## Design

- Portable attachment reference: opaque UUID assetId, sanitized filename, validated MIME, actual byte size and optional CID. Immutable account-owned asset metadata and lazy 64 KiB base64 chunks. Absent/incomplete is an error, including advertised zero bytes without a sealed asset. A sealed empty asset is valid.
- Assets staged and sealed before reference use; per-account ownership and completeness checked again atomically on draft save and queueSend. Draft revisions keep complete reference lists with body/recipients. Queue captures refs and a draft revision guard, so delayed saves and uploads cannot mutate the queued snapshot. Send dispatch hydrates captured refs into bounded bytes via a backend helper; definitive asset errors become nonretryable ProviderError before submission. Parent owns core integration.
- Incoming MIME retains all parts, including inline parts, and exact decoded bytes. Store ingestion stages bytes before committing metadata/body, updates missing metadata during IMAP body fetch, and deduplicates repeat full ingestion without stale-byte substitution. Both stores cascade account removal through assets/chunks. Referenced assets survive source-message deletion/forwarding; abandoned uploads are bounded by quota and reclaimed by explicit cleanup on attachment operations.
- RPC transfers only bounded byte chunks/base64 and IDs; never filesystem paths. UI attaches via File bytes, saves refs with local draft, removes by revision, forwards cached refs, and downloads via a temporary Blob URL. No background reads until opened. CID images resolve only on explicit local-content consent, only raster MIME, under existing sandbox/CSP; remote-image policy remains unchanged.
- Conservative 25 MiB encoded MIME ceiling, 18 MiB total decoded attachments, 100 parts, 256 MiB account asset budget. MIME builders check actual built transmission size; portable builder accounts for base64 line overhead. Parsing has an explicit raw budget. Work in chunks with yields; no idle timers or provider draft API.

## Recovery and portable backup layer

Additional red cases: 7 MiB ASCII falsely rejected (three adapters); legacy full IMAP bodies omitted from attachment capture (three adapters); oversized incoming attachment stalled ingestion (three adapters); disconnected-account import incorrectly stored attachment bytes in eager pending settings (one RPC case). All 31 precisely selected layer tests now pass. A broader earlier grep also selected unrelated IDB search setup, which timed out on the loaded host; the precise run uses a 60-second hook allowance and does not relax performance gates.

Capture states are 0 pending/legacy, 1 complete (including legitimate no-part raw mail), 2 unavailable due to a local byte limit. State 2 keeps readable body and attachment metadata, and does not fetch again on every sync. The explicit renderer-only retry account-checks the message, reopens capture and requests normal mail-provider sync. IMAP body work includes uncaptured legacy full bodies. Storage I/O errors still fail staging and preserve the previous committed message rather than claiming complete capture. A 256 MiB per-account decoded reservation includes metadata allowance so empty files are bounded too.

Backup format 2 adds an optional per-draft portable chunk manifest without local IDs. Export includes queued send asset bytes in advisory operations too; existing import intentionally does not replay sends, including unknown acceptance. Import validates all supplied chunks before creating drafts, remaps by connected account address, creates fresh account-owned asset IDs and seals before linking. Attachment SHA-256 plus metadata participates in draft duplicate detection, so byte-distinct otherwise-identical drafts survive repeated imports. Failed and duplicate staging is discarded. Attached drafts require their account connected before import; their bytes are not retained in eager settings for a disconnected account. Backup attachment bytes are capped at 32 MiB to remain inside the existing 50 MiB file import budget; an over-limit backup fails explicitly rather than silently omitting files.

Protocol evidence: the real in-process imapflow/SMTP fixture receives binary and zero-length attachments, resolves them offline, forwards them through SMTP and verifies exact bytes in both transmission and Sent APPEND.
