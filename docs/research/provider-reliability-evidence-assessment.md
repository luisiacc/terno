## Six concrete historical corrections

These are the strongest examples in this independently checked sample, not an exhaustive ranking of all 83 entries. Source paths below resolve at the named commit; report links retain the surrounding evidence and qualifications.

1. **A16 — Autosave forgot the newly created draft identity.** PR #855, 2025-05-07, `aa8cb91a9b021f5cb635b6da520bfa8e6bd1e30f`. The patch to `apps/mail/components/create/email-composer.tsx` changes URL-only identity into local draft state and calls `setDraftId(draftId)` after save. That is concrete corrective code for subsequent saves targeting the same draft. **Limit:** its only changed file is the composer; no regression test was added, and duplicate creation was not executed here. Terno needs stable draft identity, not this particular React/URL workaround. [Report A16](provider-reliability-report.md:414).

2. **B02 — An old authorization failure could clear a successful reconnect.** PR #3520, 2026-09-06, `d8fe93acf2770cae11f58cf0270dfd5e206fb869`. `apps/web/utils/auth/cleanup-invalid-tokens.ts` adds comparison with the failed credential snapshot and an `updatedAt` condition on cleanup writes. Its test adds “preserves reconnected credentials when an old request fails” and asserts no cleanup or reconnect notification. **Implication:** fence late failures against the credential generation that failed. The baseline already identifies Terno tests for this family; preserve/extend them rather than rebuilding auth. [Report B02](provider-reliability-report.md:592), [baseline auth tests](provider-reliability-baseline.md:37).

3. **B07 — Failed processing retained its dedupe lock and suppressed retries.** PR #4268, 2026-10-20, `dfb122fbb8799cdf30c0078e8196be95cf7f01bf`. `apps/web/utils/redis/message-processing.ts` replaces a five-minute mark with an owned processing wrapper that releases on failure and keeps successful deduplication. Changed tests cover preserving the original error, not deleting a replacement owner's lock, success dedupe, and concurrent runs. **Limit:** these tests do not prove lossless recovery across every cursor/worker failure. Borrow the retry-ownership invariant for local durable operations; Redis/webhooks are architecture choices. [Report B07](provider-reliability-report.md:644).

4. **B15 — Archiving while paging skipped later messages.** PR #4263, 2026-10-22, `f392d95bc067dfaa9fba7b468920aea97d7ed1b9`. `apps/web/utils/outlook/batch.ts` changes “list page → move page → next offset” into enumeration before mutation. Added `batch.test.ts` models 250 inbox messages, pages of 100, and removals shrinking the query; it asserts all 250 move. **Limit:** `continueOnError=true` still permits mutation of an enumerated prefix after a listing failure; the added failure test fails the initial listing, not a later page. This is strong evidence for stable bulk targets, not proof the entire bulk workflow became atomic. [Report B15](provider-reliability-report.md:730).

5. **B21 — A sent message became an apparent failure when metadata could not be read.** PR #4076, 2026-10-08, `ab0d9e8eda03166217479f2dc1ee7177306d29e7`. `apps/web/utils/outlook/draft.ts` moves conversation-ID retrieval before submission and returns known IDs afterward. Added `draft-send.test.ts` makes any post-send read fail with 404/403/other error, expects success, and asserts one submission. **Implication:** optional post-send work must not convert acceptance into an ordinary retry. **Limit:** this patch does not prove Terno's separate local-completion failure candidate T01; that requires fault injection in Terno. [Report B21](provider-reliability-report.md:794), [T01](provider-reliability-report.md:81).

6. **B23/B24 — Missing attachment bytes were treated as usable content.** PR #4081, 2026-10-08, `361729317eb9eb99c80273acb46f9e68a077d13c`. `apps/web/utils/outlook/attachment.ts` adds raw-download fallback when inline bytes are absent, preserving explicit zero-byte files. Added tests require binary bytes, propagate failed raw downloads, and accept 34,877 actual bytes against 35,137 metadata bytes. **Implication:** distinguish missing content from an empty file; verify actual bytes. B23 and B24 are **one patch**, not two independent incidents. Its size policy is provider-specific, not a universal integrity check. [Report B23–B24](provider-reliability-report.md:814).

Tests above were read, not executed. Their fixtures establish intended, concrete failure models; they do not measure live-provider frequency or guarantee today's tests pass.

## Independent protocol confirmations

- **Gmail history expiry is a documented recovery requirement.** An out-of-range `startHistoryId` returns 404 and requires full synchronization; this does not make every message-fetch 404 a history-expiry event. [Google synchronization guide](https://developers.google.com/workspace/gmail/api/guides/sync#limitations).
- **SMTP uncertainty and partial recipients are real protocol concerns.** RCPT replies apply per recipient (§3.3); a timeout waiting for the final DATA reply can produce duplicates (§4.5.3.2.6). Therefore our inference is to retain recipient outcomes and distinguish uncertain submission from explicit rejection. This supports the invariant, not a claim that either source fixed a specific SMTP incident. [RFC 5321 §3.3](https://www.rfc-editor.org/rfc/rfc5321.html#section-3.3), [§4.5.3.2.6](https://www.rfc-editor.org/rfc/rfc5321.html#section-4.5.3.2.6).
- **Graph sent-copy visibility can lag submission.** Microsoft explicitly warns that fetching the Sent Items copy may not succeed immediately, independently supporting B21's failure model. [Immutable IDs with sending mail](https://learn.microsoft.com/en-us/graph/outlook-immutable-id#immutable-id-with-sending-mail).
- **Graph batch HTTP 200 does not mean every operation succeeded.** Responses can be reordered and carry individual statuses. That independently validates B20's current-safeguard rationale, without turning it into a separately verified historical incident. [Microsoft JSON batching](https://learn.microsoft.com/en-us/graph/json-batching#processing-the-json-batch-response).

## Decision for Terno

Treat the report as a source of invariants and fixtures, not 83 required implementations or 60 demonstrated failures. The baseline already separates existing coverage (`E`), required validation (`R`), capabilities (`C`), and local adaptation (`L`); its broad worklist is planning output, not additional independent proof. Neither document establishes that every capability must ship now. [Baseline interpretation](provider-reliability-baseline.md:5), [duplicate consolidation](provider-reliability-baseline.md:228).

For supported capabilities, prioritize accepted-send/local-completion failure injection, stable destructive-action targets, auth generation fencing, and recoverable sync/partial outcomes. Preserve existing coverage before adding machinery. Graph-specific fixes become requirements when qualifying Graph support; attachment/draft races become requirements when those transports are implemented. Hosted scheduling, server staging, and distributed locks need local equivalents only where the same failure can occur. Unmerged proposals and unresolved reports justify investigation, not automatic implementation.
