# Tauri v2 versus Electron: primary-source migration notes

Researched 2026-10-29 for Terno's macOS-first, privacy-focused desktop evaluation. Scope: upstream documentation and first-party API references only; the parent owns Terno architecture inspection and the final recommendation. **Confirmed** means documented upstream, not exercised in Terno. **Inference / untested** identifies migration implications requiring qualification. No implementation, builds, tests, profiles, credentials, or commits were involved. Only this file is owned by this research task.

## Engines, size, memory, and energy

- **Confirmed:** Tauri v2 uses WKWebView on macOS, WebView2 on Windows, and WebKitGTK on Linux. Its Rust core and WebView processes form a multiprocess application; the system WebView library is dynamically linked rather than included in the executable. Electron distributes Chromium and Node with the application. This supports a potential distribution-size advantage, not a measured Terno RAM advantage. [Tauri process model](https://v2.tauri.app/concept/process-model/), [Electron security and bundled components](https://github.com/electron/electron/blob/main/docs/tutorial/security.md).
- **Confirmed:** macOS's system WebKit is serviced through Apple's system update mechanism; Tauri explicitly warns that unsupported macOS versions stop receiving WebKit updates. Linux engine versions depend on distribution repositories. Windows WebView2 offers automatically updated Evergreen or app-managed Fixed Version distribution; do not assume every deployment is Evergreen. [Tauri engine versions](https://v2.tauri.app/reference/webview-versions/), [Microsoft runtime distribution models](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/evergreen-vs-fixed-version).
- **Inference / untested:** a small Rust executable does not measure the core + WebContent + networking/GPU + optional Node sidecar/worker footprint. System engine code still consumes resources. Compare the whole application, handle shared-memory accounting consistently, and distinguish download size, installed size, startup, steady-state memory, active CPU, idle wakeups, and energy. Rust does not change the cost of React work, DOM layout, HTML mail, editor operations, or GPU compositing inside the WebView. Backend rewrites and sidecar IPC can change those costs independently. **No numeric size, RAM, rendering-speed, or battery claim has been measured on Terno.** The documented process separation is the basis for this measurement requirement, not evidence of which engine wins. [Tauri process model](https://v2.tauri.app/concept/process-model/).

## Backend: Rust port versus packaged Node

- **Confirmed:** Tauri commands call Rust; a Node backend is a separate sidecar, not an embedded Electron main process. Tauri supports `bundle.externalBin` with target-triple-specific binaries, and its Node guide currently demonstrates `@yao-pkg/pkg`. That guide's example handles one short-lived command; it explicitly directs long-lived applications toward an appropriate IPC design, such as pipes or local sockets. [External binaries](https://v2.tauri.app/develop/sidecar/), [Node sidecar guide](https://v2.tauri.app/learn/sidecar-nodejs/).
- **Packaging options / inference:** (1) port backend services to Rust; (2) package Node code into a sidecar executable; or (3) bundle a private Node runtime plus JS, worker files, and dependencies as resources. Tauri's binary/resource mechanisms permit the latter construction, but do not supply a ready-made Node service supervisor or certify dependency compatibility. A retained Node service needs lifecycle, bounded IPC, cancellation, crash recovery, and packaged-path handling. It also retains a runtime that Terno must patch. Never depend on the user's system Node. [Binary bundling](https://v2.tauri.app/develop/sidecar/), [resource bundling and path resolution](https://v2.tauri.app/develop/resources/).
- **Confirmed:** `node:sqlite` is a Node built-in, not a browser API; `DatabaseSync` operations in Node 24 execute synchronously. `worker_threads` runs Node JavaScript in parallel; a worker entry can be a real file/URL or evaluated source. **Inference:** a Rust-only migration must replace these APIs and preserve transaction, scheduling, and worker-isolation behavior; retaining Node can preserve them only if the selected packaged runtime supports the exact APIs. A Tauri SQL plugin is not proof of semantic parity with an existing database layer. [Node 24 SQLite](https://nodejs.org/docs/latest-v24.x/api/sqlite.html), [worker constructor](https://nodejs.org/api/worker_threads.html#new-workerfilename-options).
- **Confirmed:** Node's single-executable application (SEA) packaging is version-sensitive. Node 24 documents a single embedded CommonJS script, built-in-only injected `require()` unless a filesystem loader is created, and `__filename` equal to the executable path. Its platform-support section currently lists macOS arm64 and explicitly excludes x64 from supported/tested SEA targets. Newer Node documentation describes additional packaging features; do not apply them to an older packaged runtime. **Untested:** bundler inclusion and resolution of worker entries, worker imports, `node:sqlite`, dynamic modules, and native addons. A successful development-mode launch establishes none of these. Intel support, if required, can rule out a particular SEA route without ruling out private-runtime packaging. [Node 24 SEA](https://nodejs.org/docs/latest-v24.x/api/single-executable-applications.html), [current Node SEA](https://nodejs.org/api/single-executable-applications.html).

## Privacy boundary: capabilities are not a network firewall

- **Confirmed:** capabilities govern access to Tauri IPC commands by labeled windows/webviews and permissions/scopes. Remote API access is opt-in through URL patterns; local app URLs default to enabled for a capability. A matching `windows` entry grants the capability to all webviews in that window regardless of `webviews`; overlapping capabilities combine privileges. A DOM iframe is not a separately labeled Tauri webview. [Capability reference](https://v2.tauri.app/reference/acl/capability/), [capability boundaries](https://v2.tauri.app/security/capabilities/).
- **Confirmed:** Tauri specifically warns that **Linux and Android cannot distinguish IPC requests from an embedded iframe and its containing window**. Capabilities also do not protect against insecure Rust, incorrect scope checks, intentional backend bypasses, or unpatched engine flaws. **Inference:** avoid granting mail/remote content privileged IPC, and do not extrapolate macOS isolation to Linux. Audit sandboxed, opaque-origin, `srcdoc`, and same-origin mail frames explicitly; no claim about Terno's actual frame policy is made here. [Remote API access and security limits](https://v2.tauri.app/security/capabilities/#remote-api-access).
- **Confirmed:** `WebviewWindowBuilder::on_web_resource_request` is implemented only for the `tauri` URI protocol, and not external URLs such as a development server. `on_navigation` receives a URL and can cancel navigation; its signature supplies no frame identity or resource type. Neither documents Electron-equivalent arbitrary HTTPS subresource interception. Electron's `session.webRequest.onBeforeRequest` can cancel/redirect requests and exposes `resourceType`, optional WebContents identity, and an optional requesting frame that can become null after navigation/destruction. [Tauri resource and navigation APIs, 2.12.5](https://docs.rs/tauri/2.12.5/tauri/webview/struct.WebviewWindowBuilder.html#method.on_web_resource_request), [Electron WebRequest](https://www.electronjs.org/docs/latest/api/web-request#webrequestonbeforerequestfilter-listener).
- **Confirmed:** Apple's `WKURLSchemeHandler` handles custom schemes; registering a scheme already handled by WebKit, such as HTTPS, is an error. WKContentRuleList offers native compiled declarative content rules. These are different mechanisms from a callback for each request with Electron's frame metadata. [Scheme-handler restriction](https://developer.apple.com/documentation/webkit/wkwebviewconfiguration/seturlschemehandler(_:forurlscheme:)), [content rules](https://developer.apple.com/documentation/webkit/wkcontentrulelist).
- **Inference / migration gate:** any per-message “load remote content” decision currently enforced through frame-aware interception needs a new, demonstrated design: restrictive frame CSP, sanitized/re-written URLs and controlled resource fetching, separate webviews, or platform-native rules may contribute. None is proven equivalent here, particularly with simultaneous messages, redirects, CSS/font/media loads, nested frames, caches, and changing consent. Tauri CSP is enabled only when configured. The HTTP plugin's allow/deny URLs control its own `fetch`, not all WebView traffic; native Rust/Node network activity needs its own policy too. [CSP configuration](https://v2.tauri.app/security/csp/), [HTTP plugin](https://v2.tauri.app/plugin/http-client/).

## Native integration: documented coverage and gaps to qualify

- **Notifications:** current Tauri docs support desktop action buttons through `registerActionTypes` and `onAction`; “desktop actions unsupported” is outdated. However, desktop actions use only ID/title, require a listener when shown, and macOS distinguishes actions by title. With two or more actions macOS uses an Options menu, whose button itself reports the first action. Inline input is not documented for desktop action objects. Electron documents `hasReply`/reply events on macOS. **Untested:** safe action dispatch, dismissal, app-exit/relaunch behavior, and inline-reply parity; the documented Options behavior matters for destructive actions. [Tauri notification actions](https://v2.tauri.app/reference/javascript/notification/#onaction), [Electron notifications](https://www.electronjs.org/docs/latest/api/notification).
- **Dock, tray, menu:** Tauri documents app-wide numeric badges, a macOS dock text label, native tray menus/events, native menus and predefined editing items. These are available APIs, not missing platform capabilities; shortcut routing, editing/undo behavior, accessibility, and lifecycle still need parity checks. [Window badges](https://v2.tauri.app/reference/javascript/api/namespacewindow/#setbadgecount), [tray](https://v2.tauri.app/learn/system-tray/), [menus](https://v2.tauri.app/learn/window-menu/).
- **Attachments:** `onDragDropEvent` reports incoming files, hover/drop/cancel, and coordinates. This does not establish outgoing drag-to-Finder parity with Electron's `webContents.startDrag`. No equivalent outgoing-file API was identified in the inspected Tauri core references; that is a research limit, not proof it is impossible. macOS has native file promises for deferred writes, which a native bridge could use. **Untested:** incoming directory/promised-file handling, outgoing files, lazy downloads, sandbox scope, and temporary-file cleanup. [Tauri file-drop API](https://v2.tauri.app/reference/javascript/api/namespacewindow/#ondragdropevent), [Electron outgoing drag](https://www.electronjs.org/docs/latest/api/web-contents#contentsstartdragitem), [Apple file promises](https://developer.apple.com/documentation/appkit/nsfilepromiseprovider).
- **Print/PDF:** Tauri's Rust `WebviewWindow::print` opens the print dialog and currently documents macOS support with Wry; the docs also state that `window.print()` works across platforms. This is not Electron's configurable `printToPDF` API. Apple WKWebView can asynchronously produce PDF data, reachable through native integration; pagination/options/output fidelity remain untested. [Tauri print and native-webview access](https://docs.rs/tauri/2.12.5/tauri/webview/struct.WebviewWindow.html#method.print), [Apple PDF API](https://developer.apple.com/documentation/webkit/wkwebview/createpdf(configuration:completionhandler:)), [Electron PDF options](https://www.electronjs.org/docs/latest/api/web-contents#contentsprinttopdfoptions).
- **OAuth/deep links:** Tauri documents static desktop scheme registration, startup URLs through `getCurrent`, and running-app callbacks through `onOpenUrl`. macOS cannot register schemes at runtime; its guide requires a bundled app installed in `/Applications` for testing. OAuth itself still needs external-browser authorization, PKCE, callback/state validation, and provider-compatible redirects; loopback redirects are also standardized. Changing shell does not require embedded-WebView OAuth. [Tauri deep links](https://v2.tauri.app/plugin/deep-linking/), [RFC 8252 §§6–8](https://www.rfc-editor.org/rfc/rfc8252).

## Credentials and distribution migration

- **Confirmed:** macOS has distinct file-based and data-protection keychains. File-based items can use trusted-application ACLs; data-protection access depends on entitlements/access groups. Apple's data-protection query flag explicitly calls out legacy-item access as an exception. Matching a bundle ID or an item service/account string alone therefore does not prove continued access. Code identity and distribution-channel changes can trigger authorization prompts. [Apple keychain types](https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains), [ACL behavior](https://developer.apple.com/documentation/security/access-control-lists), [legacy versus data-protection queries](https://developer.apple.com/documentation/security/ksecusedataprotectionkeychain), [signing requirements](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements).
- **Inference / gate:** identify the actual old storage format and which signed executable accessed it before designing migration. Direct Keychain tokens and encrypted application blobs are different: Electron `safeStorage` protects strings using OS cryptography and stores app encryption keys in Keychain; it does not imply every token itself is a generic Keychain password. A new Rust keyring/vault is not automatically a `safeStorage` decoder. Preserve old data until successful migration is established, allow for denied prompts/re-authentication, and qualify old-signed-app → new-signed-app access using synthetic credentials only. Also check whether moving access into a Node helper changes the accessing code identity. No Terno credentials or profiles were inspected. [Electron safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage), [Apple code identity](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements).
- **Confirmed:** Tauri supports macOS signing/notarization, entitlements and minimum-OS configuration. Its updater requires an update signature, produces a macOS `.app.tar.gz` plus signature, and documents HTTPS endpoints. Updater signatures are separate from Apple code signing/notarization. Electron's built-in macOS updater uses Squirrel.Mac and requires a signed app. [Tauri signing](https://v2.tauri.app/distribute/sign/macos/), [bundle configuration](https://v2.tauri.app/distribute/macos-application-bundle/), [Tauri updater](https://v2.tauri.app/plugin/updater/), [Electron updater](https://www.electronjs.org/docs/latest/api/auto-updater).
- **Inference / gate:** existing installers, feed formats, signatures, sidecars, app identity, data locations, and rollback must be reconciled; changing the feed to a Tauri artifact is not a demonstrated Electron → Tauri upgrade path. A Node sidecar adds nested executable signing/runtime considerations. Updating Tauri does not update the installed system WKWebView; Electron engine patches arrive through an updated Electron-containing app. Neither architecture eliminates security-update responsibility. [Tauri updates](https://v2.tauri.app/plugin/updater/), [Apple nested-code signing](https://developer.apple.com/library/archive/technotes/tn2206/), [engine servicing](https://v2.tauri.app/reference/webview-versions/), [Electron update responsibility](https://github.com/electron/electron/blob/main/docs/tutorial/security.md).

## Automation and Safari/editor qualification

- **Confirmed, current-doc correction:** direct official `tauri-driver` supports desktop Windows/Linux, not macOS, because there is no WKWebView driver tool. However, Tauri's current guide recommends WebdriverIO's service and **an embedded WebDriver server that supports macOS**, without an external driver. A separate CrabNebula route also exists and requires a paid key for macOS. Thus “Tauri has no macOS automation” is too broad. Embedded testing requires additional app plugins; WebdriverIO documents debug-gated installation. Actual release-package coverage, native dialogs, and coverage of every needed command were not verified. [Tauri WebDriver guide, updated June 2026](https://v2.tauri.app/develop/tests/webdriver/), [WebdriverIO plugin setup](https://webdriver.io/docs/desktop-testing/tauri/plugin-setup).
- **Confirmed:** Playwright has an experimental Electron API. Its WebKit browser is a patched build from WebKit main, often ahead of shipping Safari; it does not drive branded Safari. **Inference:** adding Playwright WebKit web-build tests is useful but does not prove behavior in the installed WKWebView or exercise native IPC, permissions, updater, or Keychain. Existing Electron automation cannot simply be assumed to target Tauri. [Playwright Electron](https://playwright.dev/docs/api/class-electron), [WebKit browser differences](https://playwright.dev/docs/browsers#webkit).
- **Confirmed:** WebKit documents editing paths beyond keyboard events, including context-menu actions, autocorrection and `beforeinput`/target ranges. Recent Safari release notes record fixes involving contenteditable selection/focus, formatting, and IME composition. These establish version-sensitive editing behavior, not a defect in Terno. **Untested qualification:** real supported macOS/WKWebView versions, paste/drop HTML and images, selection restoration, IME/dead keys, spellcheck, undo/redo, menu formatting, drafts, iframe sizing/scroll, fonts, light/dark accessibility, and reduced motion. [WebKit editing model](https://webkit.org/blog/7358/enhanced-editing-with-input-events/), [Safari 27 editing fixes](https://webkit.org/blog/18325/webkit-features-for-safari-27-0/).

## Highest-priority migration gates for the parent

1. Demonstrate per-message remote-content enforcement and untrusted-frame isolation without assuming `session.webRequest` parity.
2. Choose Rust port or private Node packaging; qualify `node:sqlite`, workers, target architectures, service lifecycle, and signed packaged paths before estimating savings.
3. Establish actual macOS WKWebView/editor and native-feature automation; use the current embedded-WebDriver option rather than the outdated blanket macOS limitation.
4. Demonstrate synthetic-credential migration and signed installer/update continuity, including recovery and rollback.
5. Measure whole-app resource use under Terno workloads. Size alone cannot justify a RAM, latency, or battery recommendation.

These are evaluation gates inferred from the cited APIs, not confirmed Terno bugs or a recommendation to migrate. No further agents were created, per the task's explicit instruction overriding the research skill's background-agent default.
